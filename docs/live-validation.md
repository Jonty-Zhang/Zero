Later on 2026-09-28, a locally patched Windows release stage used an ignored Zero data root with the verified Codex subscription binding and the three ZCode API bindings. A task locked to ZCode GLM Flash at `high` reasoning reached `done`: Codex routed it, ZCode edited one file in its own Git worktree, `node verify.cjs` passed, a separate read-only Codex review returned `pass`, and Zero saved a result commit, one-file diff, and report. This proves one real ZCode API task path through execution, testing, review, and archive on the target PC. It does not independently prove which remote model served the turn or how it was billed.

The acceptance exposed three distinct boundaries. Zero initially blocked ZCode's reverse Write permission request; the adapter now grants a one-shot response only to a validated Edit or Write path inside that task worktree, while other permission and user-input requests remain denied or blocked. A v4 permission event could briefly outlive its approved reverse request; Zero now waits briefly for only the matching request to resolve and fails closed if it does not. A fixture check that required LF failed after ZCode wrote CRLF on Windows, so the final fixture checks the exact line after CRLF normalization. Finally, Codex's default and `elevated` Windows command runner rejected read-only snapshot reads on this PC; the previously validated process-only `unelevated` mode let the reviewer inspect the snapshot and pass. [Official OpenAI documentation](https://learn.chatgpt.com/docs/windows/windows-sandbox) describes `unelevated` as a fallback with weaker network isolation. The local stage was patched after its CI manifest was generated; a fresh CI package and installed-app ZCode task check are still required. Start Plan and a natural quota reset remain unverified.
