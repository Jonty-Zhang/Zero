# Boss 最后一阶段补充要求的验收完整性

## 已复现的问题

最后一个执行 Agent 启动时，Zero 会读取已接收的用户消息。用户在该 Agent 执行期间或自动检查期间追加的信息仍能获得接收回执，但原验收提示只包含任务原始描述和验收标准，没有这些补充消息。若不触发额外执行阶段或返工，最终验收可能完全没有看到它们。

最初使用内存 TaskStore 和生产验收提示构造函数复现；随后以真实 TaskWorker、TaskReviewer、SQLite、独立 Git 工作区及 Node 检查做完整流程复现。最后执行中、最后检查中两个场景均成功接收消息，经历检查、验收和返工后到达完成态，但实际验收提示仍缺少补充要求。没有调用真实模型、修改用户队列或读取账号配置。证据保存在 `data/verification/boss-flow-round17/`。

## 修复约束

复用 `completeCheckRun` 已有事务：封存检查结果与验收包的同时，任务从运行态进入验收态，关闭新消息准入。在这个原子边界冻结任务原文、验收标准、全部已接收的用户消息及消息位置，并与验收包绑定。

普通验收、额度暂停后的继续、崩溃恢复和返工都必须读取同一份不可变要求，不能在恢复时从当前讨论记录重建历史。新要求尚未实现时，独立验收应要求修改，沿用已有返工次数、权限和验证门槛。补充消息不能授权绕过这些约束，也不能冒充已执行的检查证据。

已进入验收的任务继续拒绝新要求；已经接收的同一请求标识仍能可靠重放回执。旧 Boss 验收包若没有完整要求快照，不得凭现有讨论或旧的通过结论自动补造历史继续交付。普通任务的历史兼容路径保持原有边界。

## 验证范围

重点覆盖最后一阶段执行中及检查中追加要求、封存失败回滚、消息准入竞态、不可变快照、普通验收与恢复读取一致、旧 Boss 包缺证据以及后续返工。只使用独立测试数据和假 Agent；不以模型回答测试替代状态及持久化断言。

## 实现

新增不可变的 `review_package_requirements` 附表，绑定原有验收包。插入仅允许在对应检查运行、任务租约和所属启动代次仍有效的封存窗口内完成；既有完成包不能事后补挂。更新和删除由 SQLite 触发器拒绝。要求总量超过 256 KiB 时明确报错并回滚封存，不截断原文。

TaskReviewer 在探测模型和读取工作区之前验证任务身份、消息类型、位置及大小，再复制快照，避免异步准备期间调用者修改输入。验收提示使用封存的目标、标准和完整用户消息，按顺序解释明确的后续修正；接收回执本身不构成实现证据。

正常验收、额度恢复、崩溃恢复、已有通过结论和已有提交操作的复用路径均检查要求快照。Store 在验收结论、返工、提交、报告和完成授权处再次校验。历史 Boss 包可以读取，但缺少快照时不能继续交付；普通任务的旧包兼容路径保留。

关键复核另外发现：验收额度暂停会把任务从 reviewing 改为 waiting，原消息入口因此重新开放。现已让 `review_quota` 等待保持封口，同请求标识和内容的已接收回执仍可重放；计划或执行额度等待继续接收要求。HTTP 返回同一准入规则，网页同步禁用已封存任务的发送入口并保留草稿。

这些验证证明要求的持久化、传递和授权边界，不证明真实模型一定正确理解并实现每条要求。Codex Desktop 的接管能力也不属于本轮变更，当前运行入口保持原状。
