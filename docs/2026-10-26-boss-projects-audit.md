# Boss projects: design and verification record

The default project flow follows the user's requested division of responsibility: the user supplies a folder, an objective and an optional free-form preference; the Codex lead designs, consults, delegates and accepts the work. Manual check commands, fixed executor choices and ordered stages remain an advanced workflow.

## Implemented behavior

- The local folder browser supports selecting an existing directory or creating its final child directory. Browsing or cancelling does not initialize projects. Preparation creates local history for ordinary and unborn Git folders, with exclusions and explicit size limits. Existing committed Git folders receive a private snapshot ref for current source files, including uncommitted changes; their branch, index and source files remain unchanged. Private refs retain queued snapshots against Git garbage collection.
- The lead resolves imprecise model names against currently verified, healthy bindings. It records the preference, actual model/effort and resolution reason. It can request independent Codex, DSH or ZCode advice before producing a bounded executable plan, acceptance criteria and real check argv. The lead owns these choices; legacy global executor defaults do not pin Boss projects.
- Every planning and consultation call receives its own persisted attempt and actual cancellation target. Codex consultations use read-only snapshot roles. DSH/ZCode consultations use disposable sanitized project copies; these Harnesses have no verified read-only CLI mode. Their edits are discarded. This is filesystem separation, not an operating-system sandbox.
- Writers run serially in one registered task worktree. Completed stages produce observed handoff evidence. At a later route boundary, the lead can inspect the staged current project and adjust only remaining stages. Successful logical stages remain frozen; interrupted physical attempts can be skipped only with matching quota, claim, predecessor and fingerprint evidence.
- Generated checks run through the existing check runner and immutable review-package gates. Check definitions freeze when validation starts. A fresh Codex session uses the persisted Boss binding for acceptance and receives accepted human updates. New human messages are transactionally rejected during acceptance, cancellation and terminal/recovery states, so an unprocessed requirement cannot be acknowledged as accepted.
- Details expose the durable task workspace, branch and applied result commit. The desktop UI identifies the output folder and offers copy-path access. It does not automatically overwrite the original folder, merge or publish results.

## Critical review and reproduced fixes

A GPT-6 Astra high reviewer inspected the architecture and independently reproduced the first two issues below. After those fixes, its final focused review found no further established P1/P2 findings. It independently reran both reproductions, five saved-plan/message contract tests, three consultation/binding/stage-budget tests and three folder snapshot tests. Its HTTP fixture was blocked before reaching the server by sandbox loopback permissions and is explicitly not counted as passed; root's permitted local HTTP runs are recorded separately.

1. Existing unborn repositories could execute a `reference-transaction` hook while preparing their initial ref. The Git helper now disables hooks and fsmonitor for each child command, without changing saved Git configuration. The independent reproduction changed from two hook invocations to none, with original config/source bytes preserved.
2. A writer quota pause created an interrupted physical stage followed by its resumed stage. The original prefix check counted both as completed work and rejected the next Boss plan. Prefix validation now distinguishes completed logical stages from proven quota continuations. The independent reproduction changed from `failed` before the second writer to `done`, with two calls to the interrupted writer and one to its successor.
3. Existing committed repositories previously defaulted to `HEAD`, omitting current uncommitted source. The default Boss submission now uses the prepared private snapshot ref. Explicit advanced/API base refs retain their explicit meaning.
4. Deep Windows artifact paths could make Git initialization exceed its legacy path limit. Boss run directories are shorter, empty Git templates are actually supplied, and isolated child Git configuration enables long paths. The regression includes a project snapshot file over 400 path characters.
5. A long consultation reply plus its provenance prefix exceeded the durable message bound. Complete advice is now retained in bounded message chunks and supplied to the lead without cutting off its final requirements.
6. Acceptance could silently inherit an unrelated global reviewer effort when the Boss had none. Boss acceptance now uses only its persisted lead binding.
7. Late messages could otherwise be accepted after the acceptance input was fixed. Admission is now guarded inside the same store transaction as message append, with HTTP 409 and matching UI disabled states.
8. Ordinary quota recovery retained its previous quota error on a resumed task. Claiming clears the active error while the append-only quota event preserves history.
9. Adaptive planning could consume the full sixteen-stage allowance after stages had already completed. Both the planning prompt and executable-plan validator now subtract the frozen completed prefix; fifteen completed stages permit only one further stage.
10. Clean GitHub runners exposed test fixtures that assumed a local verification directory existed, and a path-length assertion that depended on the host temporary directory. Worker fixtures now create their own parent directory. The long-path regression explicitly sizes its artifact directory on each host and still verifies an actual snapshot file over 400 characters; it is not skipped on Linux.

## Reproducible validation

The new source tests are `src/core/boss-plan.test.ts`, `src/orchestrator/boss.test.ts`, `src/orchestrator/worker-boss.test.ts` and `src/server/project-folders.test.ts`. They use real SQLite, Git worktrees, snapshots, the check runner, router/reviewer protocol and local HTTP detail reads with deterministic fake Harness calls. They cover cross-Harness advice and two writers, changed remaining delegation, actual generated-check execution, output provenance, cancellation, consultation/planning/writer quota boundaries, retained human requirements and rejected late messages.

The complete frontend run passed 98 React tests and 13 API tests and produced a successful production build. A synthetic local API was rendered in an isolated browser profile at desktop widths 1440 and 1920; entry, folder browser, plan, discussions, output path and settings had no page errors. Root inspection confirmed the entry and delivery screenshots. All browser-owned processes were stopped. This test did not use the real user queue or invoke model CLIs.

Local logs and hashes are under ignored `data/verification/boss-projects-root/`, `boss-critical-review/`, `boss-long-paths/` and `boss-ui-browser/`. They include preserved failing reproductions and post-fix evidence. Two initial broad Windows backend runs were not clean: 750/754 and 745/751 passed. The first exposed test deadlines that included slow real Git setup; the deadline correction retains a separate three-second cancellation-response assertion. Its remaining integrity case passed unchanged on recheck. The second encountered Git-command failures in sequence setup and a cancellation fixture's initial state; all affected files/cases passed subsequent focused rechecks (nine sequence assertions and one cancellation assertion). Their intermittent cause was not established by a passing rerun. The third full run retained default concurrency and recorded raw Git error code/signal information without retrying or suppressing errors. It passed **755/755, zero failures and zero skipped tests**, finishing at `2026-10-26T03:21:06Z` with exit code 0. This clean result does not retrospectively prove the cause of the earlier intermittent failures.

Clean GitHub CI initially exposed the missing fixture parent and path-length assumption on both Linux and Windows. Commit `9cd31feca2a3396d756d8bcb659ecd4fec0f79d2` fixes those tests. [Its replacement CI run](https://github.com/Jonty-Zhang/Zero/actions/runs/40261621527) completed with **both Linux and Windows jobs successful**. This includes the core suite, frontend tests and production builds, native Windows guardian checks, release staging, packaged manual launch and Windows installer/uninstaller smoke tests. The preceding Windows run passed 749/755 tests with only those six now-corrected fixture failures; its failing log remains preserved rather than replaced by the successful run.

No new live-provider acceptance is claimed. Model authentication/enrollment is still required before a binding is eligible. Multi-stage crash recovery retains the existing conservative quarantine boundary; quota continuation is covered separately and does not imply arbitrary crash recovery. Automatic parallel writers, unbounded replanning, native conversation-history transfer and automatic source-folder publication are not implemented by this change.
