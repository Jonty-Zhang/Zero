## 复现结果

上一轮修复了执行 adapter 的模型选择后，继续检查登记入口。两个合法模型的命名可以交叉：第一个模型的上游名称为 `second-local`，第二个模型的 Zero ID 也为 `second-local`，但 provider 与实际上游模型不同。旧 `runBindingVerification` 将两种命名空间混在 first-match 条件里，验证第二个模型时，可能选中、验证并登记第一个模型。配置顺序反转后行为不同。

唯一旧别名也受影响：入口虽然找到正确模型，后续 `markVerified` 又按同样的 OR 条件选择第一个候选，导致预期 tuple 检查拒绝合法登记。追加推理强度证明的 `markReasoningEffortVerified` 同样可能更新另一个模型。重复精确 ID 和模糊别名则可能被当作唯一模型验证或持久化。

使用真实配置存储和 `runBindingVerification`，以 Codex probe/run 内存替身回显真实随机 nonce；所有进程调用禁止，只允许受控 `git rev-parse` 内存替身。十项永久回归在旧生产代码上编译实际退出 0，测试两项通过、八项失败，实际退出 1。普通无碰撞登记和验证期间 tuple 变化拒绝是通过的正常对照。这里证明的是 Zero 的选择与登记行为，没有调用真实模型，不能据此声称外部账号已发生误用。

## 修改

将 adapter 既有的精确 ID 优先规则提取为共享 `resolveModelIdentity`，现有 `resolveModelBinding` 保留原 Harness/selector 调用范围。Codex 验证入口、锁内登记存储及追加推理强度证明共用该规则：存在精确 ID 时只接受唯一精确项；没有精确项时才接受唯一上游别名；两类歧义均拒绝。

选择不依赖配置顺序，不预先排除未验证项，也不绕过 expectedModel tuple 比较。入口仍传完整选定 tuple，配置锁内仍重新读取最新状态；模型在 nonce 请求期间变化时，旧证明继续被拒绝。其他 Harness 的登记逻辑没有改变。
