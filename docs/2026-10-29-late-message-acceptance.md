# 最后执行阶段收到补充要求的验收审查

本轮检查单阶段项目中，用户在执行 Agent 已开始后追加要求的处理。风险是执行提示已经生成，新要求可能既没有进入实现，也没有进入验收。

当前路径在 writer 启动时读取用户消息；检查完成后，存储事务再次读取全部用户原文，将其封入审核包的不可变要求，并关闭该轮消息接收。实际 Reviewer 同时收到原目标、验收标准和按时间排列的完整用户消息；未实现的新要求必须触发返工或阻塞。返工 writer 再读取用户原文。

使用真实 Worker、TaskReviewer、SQLite、Git 工作区和检查器，模型调用由替代适配器实现。首次 writer 开始后追加“Export / 导出”要求。两个实际审核提示均包含同一条完整用户原文和消息标识；第一次审核要求修改，返工收到原文并更新产物，第二次审核通过，任务到达 `done`，报告摘要确认了该要求。完整流程有一次规划、两次执行、两次验收。没有调用真实模型，也没有读取个人认证。

这一证据未证明任务全过程具备即时 Boss 聊天。单阶段任务最后一次执行结束前，没有独立的 Boss 回复环节；提问会作为用户要求进入后续执行或验收，但不保证出现直接答复。后续对话改进须保留完整原文、真实验收、取消及调用归属，不能以生成一条确认文案替代实际处理。

单独回复不宜复用规划器：规划输出必须含至少一个剩余执行阶段，且检查开始后不能修改契约。下一步宜设计只读 Boss 响应，把真实回答与具体用户消息标识关联并持久化；新要求继续走已验证的封存验收和返工链。回复重试、额度暂停、取消及崩溃后的调用归属仍需明确设计，不能把“已送达”标作“已处理”。

隔离审计证据位于本地忽略目录 `data/verification/boss-message-round23/late-message-evidence.json`。本轮将上述跨实际 Reviewer 的路径纳入 `worker-boss.test.ts`，避免只用 Reviewer stub 验证消息传递。

最终 TypeScript 编译成功，整个 `worker-boss.test.ts` 的 8 项测试通过，包含新增的完整末阶段消息验收回归、跨 Harness 咨询与接力、取消归属及额度暂停恢复。没有更改生产执行逻辑。
