# 2026-10-24：执行模型绑定的身份解析

## 已确认的问题

配置中的 Zero 模型 ID 与供应商上游 modelId 属于不同命名空间，但 Base 查找把两者放在同一个 first-match 条件中。某模型的 ID 恰好等于前一个绑定的上游名称时，路由虽然返回正确 Zero ID，执行器仍会取错绑定。真实 Codex prepare 控制生成了错误的 --model 参数；真实 ZCode isolated prepare 控制选到了另一绑定的账号配置目录。

另外，同一模型配置到 Codex 和 DSH 后，工厂把完整绑定列表传入各执行器；旧查找可能先取到其他 Harness 的绑定，导致合法 DSH 请求在探测前失败。桌面 ZCode 的 OR 查找则将唯一精确 ID 与另一个绑定的别名同时计数，造成 probe 宣布可用的模型在 run 时被误拒。

真实配置、工厂、router、composite 和 prepare 的八项隔离组合控制中，旧版四项失败、四项通过，实际退出 1。控制在进程启动前截断，桌面 peer 使用内存替身；没有调用真实模型，也不能据此声称真实账号已被误用。

## 修复范围

新增共享解析函数，调用者先限定当前 Harness，桌面路径还限定 existing-desktop selector。优先查找唯一精确 Zero ID；没有精确匹配时才接受唯一上游名称别名。重复精确 ID 和模糊别名均拒绝，结果不随数组顺序变化。解析不先筛掉未验证项，避免绕过无效精确绑定或掩盖冲突；确定绑定后继续执行原验证门禁。

只修改两个 adapter 的绑定查找和共享函数。配置、路由、组合执行器的分发规则不变，其他配置/登记入口中的静态候选不在本修复结论内。
