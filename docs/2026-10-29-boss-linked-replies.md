# Boss 在验收时回答用户消息

## 目标与选择

现有执行链会把补充要求带入密封验收并据此返工；生产入口还会发布真实验收摘要，但摘要不保证回答具体问题。本轮增加由实际 Boss 模型生成的定向回答，关联用户原消息，在安全验收点展示。

复用现有只读 TaskReviewer 调用，避免新增模型调用或执行恢复阶段。它已经使用已选负责人、净化后的只读项目快照和不可变用户要求。独立响应阶段需要新建暂停和续跑协议，直接插在 writer 后面会在额度恢复时重放 writer；本轮不采用该方案。

## 数据与行为

新封存的 Boss 审核包固定回复策略和目标消息标识。目标来自本包的用户原文，排除已经有持久关联回答的消息；重试不重算目标。旧包和非 Boss 审核保留既有兼容行为，不能改写历史证明。

Boss 专用输出增加 `userMessageReplies`，每条含用户消息标识和真实回答正文。严格校验唯一标识、准确覆盖本包目标、非空正文、单条长度及总输出界限。不得把已送达、计划摘要或验收结论伪装成定向回答。新策略下不能以缺回复的 PASS 通过；模型进程失败或结构无效只能阻塞，不能发布“已回答”。

TaskReviewer 选择和核对任务持久化的实际 Boss 模型与思考强度。回答不改变检查、计划、要求、独立验收判定或返工预算；未满足的用户要求仍需 `changes_requested` 或 `blocked`。

回答必须在 `finishPackageReview` 的现有事务中，与有效 package verdict、实际 attempt 及消息来源一起保存，不能在生产 wrapper 中先发表。存储层再次校验目标与内容，检查持久取消请求；重复提交不得产生重复回答。回答的关联信息使用可选字段保存在 Boss 消息中，历史消息不补造来源。

页面展示真实关联答复，并区分送达与回答。回答在验收时产生，不承诺即时聊天，也不另起模型调用。配额恢复沿用现有审核包协议；不能声称供应商调用严格恰好一次，进程崩溃后仍执行现有证据恢复边界。

## 验证要求

先写失败测试。覆盖新策略的逐条回答、真实模型/强度、旧包与非 Boss 兼容、空白/漏项/重复/伪造标识/超限、无效输出阻塞且不发表、失败检查保留回答、事务提交及回放去重、取消竞态和快照变更拒绝。完整 Worker 与实际 Reviewer 验证追加要求、定向回答、返工及最终交付，配额恢复不重放 writer。前端只显示已持久化关联，不能从相邻消息猜测已回答。全程使用假模型和隔离工作区。

## 实现与验证

要求快照使用可选 `replyPolicy: per_message_v1` 与 `replyMessageIds`，历史包不会补造目标。关联回答使用 `inReplyTo`、`reviewPackageId`、`reviewAttemptId`。下一轮仍携带全部用户原文，只排除已能验证到成功尝试、对应验收包与结论、相同模型和正文的回答目标；普通消息或伪造来源不算答复。

新策略的有效 PASS 与返工结论，即使目标为空，也必须匹配持久化的 Boss 模型与明确指定的思考强度。安全失败产生的无回答 blocked 可以保存阻塞结论，不能标记已回答。单条回答最多 4000 字符，回答集合最多 131072 UTF-8 字节，超限拒绝而不截断。

针对存储和实际 Reviewer 的 42 项测试通过，包括空目标模型绑定负例、旧包兼容、错误输出和事务故障注入。故障注入确认回答事件写入失败时，尝试状态、验收结论与回答一起回滚，相同尝试随后可安全重试。前端 286 项测试、请求生命周期 18 项测试和两端构建通过。

独立端到端检查使用实际 Worker、TaskReviewer、SQLite、Git、检查命令和 HTTP 读取，模型替换为隔离的假适配器。执行中追加双语要求，第一轮回答关联原消息并要求返工，第二轮仍验收全部原文但不重复回答，最终交付。写入阶段两次、验收两次，HTTP 回读得到与数据库一致的来源字段。关键复核确认模型绑定、来源去重、取消、归属及原子提交边界；不据此声称真实供应商调用经过测试。

完整 Boss 集成文件 9 项通过，含规划、执行及验收额度暂停恢复。扩展存储、恢复与取消回归初次发现额度提交测试的旧夹具没有 Boss 计划或实际模型身份；补齐夹具后该文件 36 项全部通过，原有证明、租约、快照、取消和旧包拒绝断言保持原样。该次扩展运行其余 338 项通过。
