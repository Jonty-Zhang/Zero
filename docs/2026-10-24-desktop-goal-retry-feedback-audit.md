# 2026-10-24：目标重新验收的反馈归属

## 已确认的问题

目标抽屉轮询加载新验收 attempt 时，重新验收 POST 的错误和等待状态仍属于抽屉本身。旧 attempt 的失败提示会出现在新一轮 running 或 pass 结果旁；旧 POST 尚未返回时，新 blocked attempt 的按钮也会错误禁用。允许新一轮提交后，还需要防止旧请求的 catch/finally 和成功确认覆盖新请求。

七项控制使用真实 App 和未替换的 API 客户端，只在 fetch 边界返回可控 HTTP Response。冻结旧版 App 实际退出 1：六项失败、一项通过。保留的正向控制确认当前 attempt 的 503 错误仍应可见并允许重试。

## 修复

将 busy 和错误绑定到发起请求的 attemptId，并只在当前 attempt 仍可重试时显示对应错误。每次提交递增操作标识，成功、失败及 finally 均核对标识，避免旧响应清除新请求的等待状态、覆盖排队确认或额外刷新。

新增控制覆盖轮询推进、迟到 503、新 blocked attempt 可操作、当前失败后重试，以及旧 503/202 在新请求前后返回的三种顺序。既有 stale-CAS 测试增加受控刷新：先证明当前错误可见，再加载新 running attempt 并确认旧错误消失；仍检查精确 attempt 参数和读取次数。
