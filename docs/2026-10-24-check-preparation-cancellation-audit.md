# 2026-10-24：检查命令准备阶段的取消

## 问题

TestRunner 只在 runOne 入口检查取消。启动路径解析和日志目录创建都可能异步等待，期间收到取消后原代码仍会调用 spawn，再尝试终止刚创建的子进程。Windows npm 路径解析失败时，也会把同一窗口内的取消转成普通 spawn_error。

六项启动边界控制在冻结旧版上三项失败、三项通过，实际退出 1：解析完成后取消和日志目录等待期间取消均记录到不应出现的 spawn 调用；解析失败控制未保留原取消 reason。探针在真实 Node spawn 导出边界抛错，阻止了实际子进程创建，不能据此声称真实检查产生了副作用。

## 修复

在解析失败分支、解析完成后和日志 mkdir 完成后各检查 AbortSignal，保留原始取消 reason。准备阶段取消继续采用已有入口的拒绝契约，未增加新的检查结果类型。日志目录本身可能创建完成，取消后不打开日志流或创建进程。启动后的终止流程没有改动。

## 验证

修复后六项控制通过；与原 TestRunner、Windows npm/npx 解析控制合计 11/11，实际退出 0，包含真实隔离 npm 包检查和不经 shell 的参数验证。编译实际退出 0。

随后四个任务取消、Worker、完整性及心跳测试文件共 60/60，实际退出 0，无取消或跳过。覆盖运行中检查取消、崩溃与额度恢复、返工检查、检查/审查/提交门禁、多 Agent 阶段接力及 201 文件任务的完整交接。这是受影响分支回归，不是当前全项目核心套件。

Astra high 针对这一关键进程边界完成独立复核：独立编译实际退出 0，定向七项和独立补充三项均通过；直接观测到取消后不开日志流、不 spawn、保留对象 reason，顺序检查收到取消后不继续下一项。两个独立编译模块与根 dist 逐字节一致，源码差异确为三处 guard。只读核对 Worker 正常和恢复检查路径均传入活动取消信号，拒绝进入既有取消/中断处理，结论 APPROVE。
