# 验收额度恢复后直接通过的提交恢复

## 已复现的问题

同一服务启动周期中，任务完成实现和检查后，验收因额度不足进入等待。额度恢复后的新验收直接通过，任务却停在验收状态，无法创建提交操作。相同流程在服务重启后能够完成。

原因是恢复执行统一使用了跨启动代的提交授权，而同代额度恢复本来就不创建跨代恢复链。不能通过补造恢复记录或允许空链来绕过这个限制。

## 实现

同代额度恢复产生的新通过结果可以使用普通提交路径，但必须由存储层在创建提交意图的同一事务内证明：当前租约仍有效，最新领取和额度恢复事件相互匹配，原检查包属于当前启动代，新验收在此次恢复之后开始并由当前持有者完成，且完整检查、需求快照和提交前工作区检查一致。

执行器须传递完整恢复依据，并明确区分本次产生的验收结果与已保存结果。存储层不能把调用方的布尔值、缺少恢复记录编号或相同代编号当成授权。旧包、跨代恢复以及已有恢复链的任务继续使用严格链验证。返工后生成的新检查包须保留正常提交能力，同时不能借新包分支绕过旧包的恢复检查。

已在普通提交意图的事务内加入上述授权。缺少调用方依据也不能绕过当前额度领取的检查；提交前检查必须包含完整快照并在有效时限内。旧的通过结果不能冒充本次恢复后新产生的结果，取消、租约变化和已有提交操作仍会阻止创建。

返工新包通过真实返工开始、检查完成和检查包创建事件的顺序识别，并绑定当前检查持有者和验收持有者。返工再次遇额度并换持有者时，无跨代领取记录的任务须有最新真实同代返工额度恢复事件；已有跨代领取记录则验证原续接链。没有通过补造恢复记录、允许空链或放宽最终完成条件来解决问题。

## 验证

使用真实 Worker、验收器、SQLite、Git 工作区和 Node 检查，模型输出由测试适配器提供。独立编写的五场景脚本先得到三项失败、两项跨代对照通过，再用同一脚本得到五项全部通过：同一持有者、换持有者、多次额度等待、重启恢复，以及重启后再次在同代恢复旧包。实现、检查和检查包均保持一次，需求快照字节不变，提交和报告各一次；同代路径没有新增跨代领取记录。

存储层 137 项回归全部通过，其中新增提交授权测试 36 项，覆盖缺失或错误恢复依据、旧结果和事件顺序、持有者或启动代变化、过期租约、取消任务、历史包、工作区检查不一致、重复提交和缺失或损坏的 Boss 需求快照。原有严格链和报告恢复回归保持通过。独立复核另实际运行当前版本的 36 项守卫，并直接核对五份 SQLite、Git 分支和完整报告内容、大小及哈希。

Worker 恢复与 Boss 需求回归共 14 项通过，含五种直接通过路径、提交及报告崩溃边界，以及“验收额度恢复后返工再次遇额度，再换持有者或重启”的两条组合路径。组合路径先暴露新校验误挡合法返工的问题，再修复并验证；没有增加修订次数。五种直接通过路径已纳入仓库中的 Worker 测试，随 CI 执行。

关键授权实施经 Astra 复核，未发现阻断问题；其额外六项返工新包正负例全部通过，包括缺少开始事件、缺少新包创建事件和错误持有者的拒绝。前端 253 项及生产构建通过，之前 Linux CI 暴露的 WebCrypto 测试等待已单独修正并提交。

测试未调用真实模型或更改真实用户任务。旧 Boss 包缺失需求快照导致无声等待的问题仍已知，本轮没有将其冒称已修复；按本轮范围停止扩展。
