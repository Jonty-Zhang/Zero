# 目录浏览地址修改后的响应归属

本轮是用户要求的最后一轮，完成修复、验证、独立复审和推送后暂停，不继续发现下一批问题。

实际组件复现了同一个地址归属问题的两种表现：读取目录 A 的请求尚未完成时输入 B，A 的响应会覆盖 B；已经显示 A 后修改浏览地址，旧目录的选择/创建操作仍可能选中 A。用户输入的新地址尚未确认，不应被旧请求改写，也不应继续作为选择旧项目的依据。

沿用现有 React 表单和 AbortController。编辑浏览地址时，使旧请求失效，结束旧请求的加载状态，清除旧目录列表/错误和基于旧目录的新文件夹名称；保留新地址，允许立即点击“打开路径”或按 Enter 重新确认。旧请求即使忽略取消、迟到成功/失败，也不能覆盖新输入或新请求结果。只有与最近一次成功浏览相对应的当前列表才能用于选择目录或组合新文件夹路径。打开路径仍由原 API 规范化，不在前端猜测路径大小写、链接或等价关系。

原项目路径、目标、偏好和未确认提交身份不因地址栏编辑而改变。浏览或编辑本身不准备项目、不创建任务、不调用模型；新文件夹仍在明确选择并提交项目后才准备。本轮不改变后端目录访问、权限、模型配置或整体布局。

验收覆盖迟到成功和失败、已显示列表后编辑、随后确认 B 并正常选择/创建、清空地址与重新打开、IME Enter 和既有取消/导航行为。先保留实际错误结果，再运行常规回归与完整 web 测试、API 请求测试和 web 构建；独立复核异步边界。所有模型/准备/任务调用为假 API，证据和运行配置均在仓库内。

验证结果：隔离实际组件先复现四项失败；加入常规套件后八项新增测试为七项失败、一项通过，随后修复通过。最终相关组件测试 106/106、完整 web 368/368（23 文件）、API 请求测试 19/19 及 web 构建全部通过。独立五项交互复核通过，包括新目录成功/失败后旧请求再返回、规范化后的新目录及新名称保留、IME Enter 和未确认提交身份保留，没有阻塞发现。

仅四行共享地址编辑处理及输入绑定改变产品行为，没有核心/后端改动。构建后的 HTML 和入口 JavaScript 已由本地 HTTP 200 返回，逐字节/哈希与已验证构建一致；这不是页面目视验收。原始失败、常规与独立验证日志、退出结果及源码/构建哈希位于 `data/verification/frontend-round34/`。提交推送后按用户要求暂停，不启动新的审查轮次；新提交 CI 如尚在运行，单独记录，不记为通过。
