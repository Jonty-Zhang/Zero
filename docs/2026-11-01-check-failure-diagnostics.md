# 检查失败诊断进入返工上下文

Round 31 已复现：普通非零退出的检查只向返工执行者传递状态和退出码，真实 stdout/stderr 留在日志文件中；因此执行者虽然知道检查命令，仍不知道原先失败原因。

本轮沿用 TypeScript、现有 CheckResult 持久化和共用返工入口。选择在 TestRunner 观察进程输出时，直接生成每个流至多 4096 UTF-8 字节的首尾摘要，随结果持久保存。摘要分别说明是否截断，即使未配置日志目录也可用。完整日志的原有限制和行为保持不变。正常检查、超时以及异步启动失败均保留已观察的输出；取消不改变现有任务控制语义。

返工简报保留原任务、全部失败项原有的编号/状态/退出码/至多 500 字符错误、审查要求和验收条件，另附 JSON 编码、明确标为不可信工具输出的诊断。不额外复制已经传递的完整 argv 合同或任意日志路径。诊断 JSON 总量最多 64 KiB UTF-8，超限时缩短文本或省略诊断，并如实记录省略；不得挤掉原任务或改变授权。传递失败结果的两个正常入口和持久恢复入口共用同一格式。旧记录、合成完整性检查以及尚无输出的启动失败若没有摘要，显示诊断不可用；不假装已从历史日志恢复。

此方案不读取 CheckResult 中任意日志路径，不增加文件读取权限，不新增模型调用，不改变检查执行/验收合同。相较重新打开路径，结果内摘要直接对应被持久记录的那次进程观察，也避免目录包含、链接逃逸和恢复期日志替换问题。代价是旧版本生成的结果仍只能提供原有失败元数据。

验证需要：真实 Node 子进程 stdout/stderr 非零失败、无日志目录、长 UTF-8 首尾与截断、空流、JSON 控制字符和总量上限；SQLite 关闭重开后摘要不变；实际 Worker 的 revise 请求确实收到原失败诊断并完成修复，且原有审查/恢复逻辑正常。全部模型使用假适配器，文件和运行配置限制在仓库内。

针对性验证已记录在 `data/verification/boss-diagnostics-round31/`：实际 Worker 回归先因缺少原失败诊断而失败；修复后 6 项核心小测试和 4 项集成/恢复测试全部通过，覆盖 SQLite 关闭重开、普通检查返工、审查返工中检查失败及 guardian 重启后的持久结果重建。独立复核 428 个编码/字节预算/原文保留用例通过，未发现阻塞问题；包括无日志目录的真实子进程分块输出、退出码 23，以及 100KB 原任务在简报中的完整保留。完整核心回归的原始结果另行记录，不以这些范围较小的通过结果替代。

完整核心回归原始结果：935 项中 934 通过、1 失败、0 取消，退出码 1。失败是 `preference RPC failures expose only fixed JSON-RPC numeric-code categories` 的假服务 RPC 超时，原始栈和结果保留在 `npm-test.log`/`npm-test.exit`。独立固定时钟还复现了该测试把合法 `elapsedMs: 777` 当作泄漏的另一处误报；两者不能混作同一失败原因，测试稳定性修复另行记录。

最终审计另行复现恢复入口的 P2：它传入整批成功/失败结果，十个成功项的大量输出占满预算，使最后的真实失败诊断被省略。现在共享简报入口先筛选非通过结果，再共同生成元数据和诊断索引。混合批次的独立精确格式化复现先失败后通过；真实 guardian 恢复回归也先因缺少失败标记而失败，再与普通返工、审查返工一起 3/3 通过。独立 428 项对抗验证在最终源码上重跑通过，并确认恢复只投影失败项。完整性门禁失败仍保留，不会随成功项一起删除。

最终构建退出码 0，源码哈希与独立复审一致。服务在确认进程归属、任务队列为空且无活动连接验证后更新，HTTP 200、网页构建一致；没有真实模型调用或目视截图验收。原始整套失败记录与最终小范围修复验证分开保留，未再运行第二套完整核心测试。
