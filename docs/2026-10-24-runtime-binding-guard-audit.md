# 2026-10-24：运行中的模型绑定一致性门禁

## 本轮确认的问题

Zero 文档要求模型登记、验证后重启服务。旧实现缺少对应运行门禁：服务捕获账号 A / 模型 A 的绑定后，如果配置把同一 Zero 模型 ID 换成账号 B / 模型 B 并重新验证，网页能力接口与路由会读取新绑定、宣布模型 B 可用，而旧执行器仍按捕获的模型 A 准备调用。

独立只读审计用真实 ConfigStore、HTTP server、工厂、TaskRouter 与 Codex run/prepare 复现，五项控制实际退出 0。其中明确断言旧版错配行为；另外四项确认未改配置时一致、重建工厂后选择新模型、新 ID 不可用、删除当前验证后拒绝路由。该审计在 prepare 后、进程创建前截断，没有调用模型。证据位于 `data/verification/runtime-binding-freshness-next-audit/`。这不是对运行中登记提供热加载支持的承诺。

## 修复

主服务为工厂传入配置读取端口。运行适配器保留启动时的固定绑定快照，在能力探测和每次新调用前，核对当前注册模型、唯一绑定、验证记录、账号及上游选择、selector 参数、CLI 版本和允许的推理强度。失配绑定从可用选择中移除，并给出确认验证状态后重启 Zero 的提示。其他未变化的模型继续可用，普通分配器/复核器偏好和执行默认值仍可在线更新。

探测结果携带绑定快照的内部不透明指纹；HTTP 能力映射和主服务候选提供器都比较自己的配置快照，避免探测期间配置变化后用新名称配旧探测结果。指纹不替代模型验证，也不会将账号配置路径加入公开能力响应。

门禁覆盖实现、修订、Codex 分配和任务/总体复核共用的执行适配器。已经进入执行器的调用保留原快照，不重建或替换活动执行器。新的异步配置检查在等待前登记取消状态；等待期间取消可阻止之后准备调用，已启动的调用仍把取消转发给原执行器。
