# Boss-led projects

The user supplies a folder, an objective, and an optional natural-language lead preference. Zero prepares ordinary or new folders without requiring the user to understand Git. A Codex Boss owns investigation, design, consultations with other configured models/harnesses, decomposition, delegation, verification, revisions and the final explanation.

The default UI must not ask for Git refs, test commands, retry counts or a prewritten agent schedule. Existing low-level task and sequence APIs remain available as explicit advanced controls. Model preferences are user text, distinct from the resolved, executable binding. An unavailable model must never be silently presented as the model actually used.

Planning runs on a bounded project snapshot. All Boss/consultant calls have durable attempts, exact cancellation ownership and recorded messages. Non-Codex consultations use disposable snapshots, not write access to the task workspace; this is not an OS sandbox. Advice returns to the Boss before an executable plan is accepted. Plans contain real checks, acceptance criteria, an internal revision budget and bound execution stages. An optional user message is persisted immediately and consumed at the next planning boundary.

The store atomically saves the plan and effective execution contract under a live lease. Original user criteria and completed stages are preserved. After each first-pass stage, the Boss may replace only the not-started suffix. Once validation begins, check definitions and acceptance criteria are frozen. The existing worktree fingerprints, immutable check/review packages, independent Codex acceptance, cancellation and quota protocols remain authoritative; a planning model saying 'done' cannot bypass them.

This change does not turn staged serial writers into parallel writers. Recovery must continue to fail closed at any boundary without an existing evidence-backed continuation. No new automatic replay or blanket crash-recovery claim follows merely from adding planning.

Acceptance requires tests through real Store/Worker/HTTP/UI contracts: ordinary and new folders; no hidden parent-repository expansion; persisted planning and messages; actual cross-harness consultations/delegation using controlled adapters; dynamic plan suffix changes; automatic meaningful checks and separate lead acceptance; cancellation and quota; legacy task compatibility. Model calls and real external-account setup are not implied by a passing fixture.
