# 不追加要求的发送回执确认

## 问题

补充消息可能已被服务端接收，但浏览器在收到响应前超时。如果随后任务进入验收或验收额度等待，页面会关闭普通消息入口；虽然原回执仍可读取，用户却没有确认按钮。

不能简单重发普通消息来确认：任务可能在确认前已从验收进入返工，重新开放消息入口。如果原消息从未到达，普通 POST 就会追加新要求，这与确认操作的含义不同。

## 实现

新增“确认发送结果”，仅针对此前发送失败且内容未变的消息可用。验收关闭普通入口时，确认仍可进行；未发送过或改成其他内容的草稿不能借此提交。普通发送与确认共享每任务的发送锁、操作标识及编辑版本保护。

客户端使用原始任务路径、内容摘要和原请求标识，不为确认生成新标识，也不把原文明文写入浏览器存储。请求显式携带 `receiptOnly: true`；服务端进入独立的只读分支，按任务、原内容和请求标识查询持久化回执，绝不调用新增消息方法。

已有回执返回原消息并清除不确定请求标识；查不到返回明确错误并保留草稿。存储不支持查询时返回不支持错误，不能退回普通发送。确认请求缺少标识、内容或任务不匹配时拒绝。即使任务已经恢复执行，只读意图仍保持，不会新增要求。

回执文案改为“已送达”，不把确认历史消息表述为仍在等待处理。

## 验证

真实 App 与真实 API 客户端的四项场景覆盖验收、验收额度等待、未发送草稿控制，以及任务已回到执行但原消息不存在。独立 HTTP/SQLite 检查确认原回执一致、缺失回执不插入、任务和内容绑定、旧存储不降级；原始失败及协议调整日志保留在本地验证目录。

后端消息与验收定向测试 16 项、原有 Store/API 回归 143 项、前端请求生命周期 16 项均通过；完整网页测试 253 项和生产构建通过。独立复核另执行 4 项真实页面及 2 项真实 HTTP 场景，全部通过，无跳过。没有创建真实用户任务或调用模型。

恢复审查另外确认了同代额度恢复直接通过无法提交、旧 Boss 包缺快照时无声等待两个问题，证据单独保存；这两个问题不冒称已在回执修复中解决，将分别修复验证。

后续 GitHub Linux 测试暴露一处测试时序问题：原生 WebCrypto 摘要可能在 React 的微任务刷新之后才完成，确认点击后的请求次数断言因此过早执行。测试改为等待实际请求边界，保留回执标识、只读载荷、消息不增加、草稿及交付状态的全部断言；没有增加固定休眠或放宽结果。修正后完整网页 253 项及生产构建再次通过，远端结果须以新提交的 CI 为准。
